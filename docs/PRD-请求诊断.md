## 1. 目标与边界

把一次日常请求的各次发送、重试等待、手动改投、耗时和失败原因组织成可筛选、可展开的诊断记录，减少人工搜索文本日志。

用户明确只做请求诊断：不做模型实测、供应商历史质量汇总或排行、速度指标、费用统计、自动换 Key、账号登录、配置导入导出。**不增加“收到有效回复才算成功”的校验，不修改现有成功/失败判定。**

诊断只观察既有控制流；转发字节、请求头、重试、超时、取消、手动切换、保活和统计行为不变。后台准备原有的有效上下文校验不修改、不扩展到日常请求。

## 3. 采集规则

- 复用原完整 UUID、请求登记、最终内部请求分类和单调时钟；后台准备代理、HEAD、健康请求、模型列表及访问限制拒绝不纳入日常诊断。
- 请求正文可能补充内部请求识别。发布诊断开始事件前确认最终登记状态；正文读取失败按原登记分类处理，不为诊断新增识别规则。
- 区分外层尝试序号、实际出站发送序号、原计额重试次数。认证格式兼容、缓存兼容和手动改投单独标识，不能冒充计额重试。
- 发送目标取本次实际快照，不能用切换通知中的瞬时目标替代。决定重试/改投与真实发送分别记录，取消后未发出的请求不伪造发送记录。
- 保存计划等待、实际等待和等待结束原因。退避被取消、到期或改投中断不记成正常结束。
- 原业务结果、流结束、下游交付及诊断完整性分别记录；诊断最终收尾幂等，不重复调用统计计数。
- 首字、错误码、中文错误解释、上游请求编号和事件类型复用现有解析结果；不反解析格式化日志，也不重新判断响应是否有效。
- 单调时钟计算耗时，墙钟只显示时间及决定归档日期。并发回调使用每请求递增序号排序。

## 4. 安全与独立存储

- 白名单记录：客户端、完整请求编号、时间、规范化接口类别、安全模型名、供应商/Key ID 及显示名称、状态码、安全错误标识、固定中文解释、已有首字和总耗时。
- 不保存请求/响应正文、任意原始头、密钥、本地口令、完整 URL 或查询串、原始异常文本和会话正文；不序列化完整快照或请求上下文。
- 事件位于 `{日志目录}/data.db` 的 `diagnostic_events`，不完整标记位于 `diagnostic_marks`；与每日统计共库、与配置分库。事件 JSON 字段与业务语义保持，旧 `request-diagnostics` 文件夹保留且不再读写、不导入历史。原文本日志保持，不重复写用量或耗时日志，不解除文本重试节流。
- 请求按开始时的本机自然日归档，跨午夜仍属于开始日；保留今天至今天减六天。读写和启动复核范围，安排下一本地午夜后台清理；删除失败明确提示，查询仍排除过期记录。
- 每次运行使用独立会话 ID，恢复使用完整 UUID 与事件序号；数据库自增 ID 用于增量读取。旧会话没有收尾时显示“结束状态未记录”；不能编造失败、总耗时或完整结果。已记录成功但缺少交付收尾时保留成功，并单独标记交付未知。
- 代理非阻塞入队，固定容量 4096 项，单事件上限 2 KiB。单后台写入器每秒或累计 256 项刷盘；退出在代理收尾后最多等待 2 秒。
- 每日事件负载按 `payload_bytes` 累加限制为 64 MiB，保留控制标记预留；该值是逻辑负载上限，不限制 SQLite 页、索引和 WAL 的物理文件大小。超过容量、队列满、磁盘异常或坏记录时显示“诊断记录不完整，不影响请求转发”，不阻塞或改变代理行为，不伪造丢失记录的数量或结局。
- 查询在后台执行，可取消；按所选日期读取并缓存有限结果，不一次加载 7 天历史，不在界面线程查库，不因每次刷新扫描完整历史。
- 从新版本开始记录，不从旧日志补造完整尝试经过。
